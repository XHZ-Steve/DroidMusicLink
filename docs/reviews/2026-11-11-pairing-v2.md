# Pairing v2 incremental security review

Scope: read-only review of `windows/src/Bridge.cpp` and `Bridge.h`, Android `PassiveLinkService.kt`, `PairingSas.kt`, `PairingStore.kt`, plus the phone confirmation callback and Windows setting conversion. Checked commit/reveal ordering, TLS certificate binding, credential release and persistence, confirmation lifetime/socket association, cancellation/replay/rate controls, and the reported boolean persistence fix. No source changes made.

## Findings

No confirmed security or correctness finding in the reviewed pairing path.

## Evidence

- Windows creates a 32-byte client nonce, sends only its SHA-256 commitment, and reveals the nonce only after receiving a single well-formed server commitment (`Bridge.cpp:83,96`). Android similarly creates a 32-byte server nonce and sends its commitment at `pair_begin`; it verifies the client's reveal before sending `pair_compare` (`PassiveLinkService.kt:117-128`). Windows verifies the server reveal against the commitment (`Bridge.cpp:97`). Both sides derive the six-digit code from the certificate fingerprint, both nonces, and client ID (`Bridge.cpp:81,97`; `PairingSas.kt:11-16`).
- Windows captures the peer certificate SHA-256 digest on the live TLS connection. Pair comparison requires the Android-reported device ID to equal that observed digest; saved credentials are sent only when the observed digest matches the saved pin (`Bridge.cpp:40-50,97`). `sslErrors` allows only the listed trust/name errors for this connection, and the source explicitly keeps that temporary trust separate from credential pinning (`Bridge.cpp:39-45`).
- Android confirmation is created only after a valid reveal. Its callback closes over the same connection and exact `Challenge`; it must atomically remove that challenge, receive approval, have an open socket, and be within expiry before adding/publishing a token (`PassiveLinkService.kt:128-142`). Cancel and socket close clear challenge/pending state (`PassiveLinkService.kt:92,145`). Challenge expiry is 120 seconds; Windows pairing UI timeout is 90 seconds (`PassiveLinkService.kt:118,142`; `Bridge.cpp:55,83`).
- Android tracks message IDs with `ReplayWindow`, rejects repeated IDs, limits each socket to 30 messages/second, and limits pairing attempts per remote address to five per five minutes (`PassiveLinkService.kt:71-72,98-115`).
- Windows boolean settings are normalized on read and invalid values are rejected on write; the test covers persisted string booleans (`Bridge.cpp:114-124`; `windows/tests/core_tests.cpp:12`). This matches the reported persistence fix.

The review did not establish an exploitable path that sends a saved token to a certificate other than its pinned identity, bypasses phone approval, or reuses a pairing challenge.
